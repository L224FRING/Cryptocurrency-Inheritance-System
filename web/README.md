# Inheritance Vault Web Console

Next.js (App Router) + TypeScript + Tailwind + wagmi/viem frontend for the
existing `InheritanceVault` / `VDFVerifier` / `FROSTVerifier` contracts and the
Rust `frost-service`.

Two roles:

- **Owner** (`/owner`) — set a beneficiary, deposit ETH, check in (vault + VDF)
  and run the FROST DKG ceremony.
- **Trustee** (`/trustee`) — prove owner inactivity with a VDF proof, collect a
  threshold FROST signature over the release hash, and call `vault.release()`.

The Next.js route handlers under `src/app/api/` shell out to the local
`frost-service` / `frost-relay` binaries. There is no separate backend process.

> **Demo custody warning.** The API writes every trustee share to
> `web/.frost/shares` so the whole committee can be driven from one machine. A
> real deployment would have each trustee run its own client and keep only its
> own share. Never put real funds behind this demo setup.

## Prerequisites

- Node 20+ and pnpm 10+
- Foundry (`forge`, `anvil`, `cast`)
- Rust toolchain (to build `frost-service`)

From the repository root:

```bash
cargo build --manifest-path rust/frost-service/Cargo.toml
anvil
```

## Quick start

In a second terminal, from the repository root:

```bash
web/scripts/deploy-local.sh
```

This runs `script/DeployFull.s.sol` against `http://127.0.0.1:8545`, writes the
three contract addresses to `web/.env.local`, and clears any stale FROST shares.

```bash
cd web
pnpm install
pnpm dev
```

Open <http://localhost:3000>.

## Owner walkthrough

1. **Set beneficiary** — any non-zero address, changeable until release.
2. **Fund the vault** — send native ETH to the vault contract.
3. **Run DKG** — choose `t`-of-`n` (defaults 3-of-5). The API runs
   `frost-service dkg --out-dir .frost/shares` and stores the committee state.
4. **Install group key** — calls
   `FROSTVerifier.setGroupPublicKeyCompressed(groupKey)` from the owner account.
5. **Check in** — sends a single `vault.checkIn()`. The vault rotates its
   challenge and calls `vdfVerifier.checkIn()`, so both clocks reset together.

## Trustee walkthrough

1. Advance Anvil past `vdf.lastCheckIn + requiredDelay` (11+ blocks). On chain
   31337 the **Advance 12 blocks** button calls `/api/dev/mine`.
2. **Generate proof** — `/api/vdf/prove` runs
   `frost-service vdf --t T --n N --input challenge` and returns `y` plus the
   Pietrzak proof points.
3. **Submit VDF proof** — calls `vdf.submitVDFProof(y, proof)`. This flips
   `inactivityConfirmed`.
4. **Sign with FROST committee** — `/api/frost/sign` computes
   `keccak256(abi.encodePacked("inheritance-release", block.chainid, vault,
   beneficiary, vault.currentChallenge))`, starts a relay, runs one
   `sign-party` per selected trustee and aggregates the signature.
5. **Release** — `vault.release(signature)` verifies the signature on-chain and
   forwards the balance to the beneficiary.

Any account can submit steps 3 and 5 — they are permissionless. The threshold
signature is the actual authorization.

If the owner checks in between signing and release, the vault challenge
rotates, the release hash changes, and the old signature is rejected. The UI
marks such proofs/signatures as stale.

## Configuration

`web/.env.local` (generated by the deploy script):

| Variable | Meaning |
| --- | --- |
| `NEXT_PUBLIC_RPC_URL` | JSON-RPC endpoint (default `http://127.0.0.1:8545`) |
| `NEXT_PUBLIC_CHAIN_ID` | Expected chain id (default `31337`) |
| `NEXT_PUBLIC_VAULT_ADDRESS` | `InheritanceVault` address |
| `NEXT_PUBLIC_VDF_ADDRESS` | `VDFVerifier` address |
| `NEXT_PUBLIC_FROST_ADDRESS` | `FROSTVerifier` address |
| `ALLOW_DEV_MINE` | `false` disables `/api/dev/mine` |
| `FROST_REPO_ROOT` | Override repo root used to locate binaries |
| `FROST_SERVICE_BIN` | Override path to `frost-service` |
| `FROST_RELAY_BIN` | Override path to `frost-relay` |
| `FROST_STATE_DIR` | Override share/state directory |

`/api/dev/mine` is additionally disabled when the chain id is not `31337`.

## API surface

| Route | Purpose |
| --- | --- |
| `GET /api/health` | RPC status, contract addresses, binary/share checks |
| `GET /api/frost/state` | Persisted DKG state and share indices |
| `POST /api/frost/dkg` | Run DKG (`{ trustees, threshold }`) |
| `POST /api/frost/sign` | Threshold-sign a release hash (`{ releaseHash }`) |
| `POST /api/vdf/prove` | Generate a VDF proof (`{ challenge, t, n }`) |
| `POST /api/dev/mine` | Advance Anvil (`{ blocks }`, chain 31337 only) |

## Troubleshooting

- **"Contracts are not configured"** — run `web/scripts/deploy-local.sh`, then
  restart `pnpm dev` so the new `.env.local` is loaded.
- **"frost-service binary not found"** — run
  `cargo build --manifest-path rust/frost-service/Cargo.toml`.
- **Owner actions revert with `not owner`** — connect the Anvil account 0
  address (or the `DEPLOYER_PRIVATE_KEY` used for deployment).
- **`submitVDFProof` reverts with `too early`** — mine at least
  `requiredDelay + 1` blocks first.
- **`vault.release` reverts with `invalid signature`** — the owner checked in
  after signing, the chain id changed, or the FROST key installed on-chain does
  not match the shares. Re-run DKG, then redeploy and install the matching group
  key, then re-sign.
- **`signature already used`** — replay tracking lives in `InheritanceVault`;
  only `vault.release()` consumes a signature. Generate a new one with
  `/api/frost/sign` if the vault state changed.
- **`group key already set`** — the FROST verifier key is one-shot. Redeploy the
  contracts with `web/scripts/deploy-local.sh` and re-run the DKG ceremony to
  install a different committee key.
